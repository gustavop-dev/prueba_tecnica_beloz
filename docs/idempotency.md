# Idempotency

> Status: **draft**.

Guarantees INV-4: no money operation is applied twice, no matter how many times it is retried. The rationale is in [ADR 0002](decisions/0002-idempotency-keys-and-request-fingerprint.md).

## 1. Idempotency key

| ID | Rule |
| --- | --- |
| IDEM-1 | Every `POST` that moves money or changes state requires an `Idempotency-Key` header. |
| IDEM-2 | The key is a UUID generated by the client. A missing or malformed key is rejected with `400` before any effect. |
| IDEM-3 | Covered endpoints: every `POST` in [api.md](api.md). |

## 2. Idempotency record

| ID | Rule |
| --- | --- |
| IDEM-4 | Records are unique on `(principal, endpoint, key)`, enforced by a PostgreSQL `UNIQUE` constraint. `principal` is the authenticated caller (customer or provider). |
| IDEM-5 | Each record stores `request_hash`: the SHA-256 of the request body. |
| IDEM-6 | Each record stores the response that was returned (status code and body). |
| IDEM-7 | The record is written in the same database transaction as the effect: both commit or neither does. A request that fails technically leaves no record and can be retried safely. |
| IDEM-8 | `endpoint` is the HTTP method plus the concrete path, including path parameters (e.g. `POST /accounts/<id>/repayments`). The account id usually travels in the path, not in the body, so a key reused for the same body on another account must not match. |
| IDEM-9 | The hash is computed over a canonical form of the body (keys sorted, no insignificant whitespace), so the same logical request always produces the same hash regardless of how the client serialized it. |

## 3. Behavior

| Situation | Result |
| --- | --- |
| New `(principal, endpoint, key)` | Execute the operation and store the record with its response. |
| Same key, same `request_hash` | Do not execute. Return the stored response (replay). |
| Same key, different `request_hash` | Do not execute. Reject with `422`: the key was reused for a different request. |
| Same key while the first request is still in flight | The second request waits and then gets the replay (see IDEM-10). |

| ID | Rule |
| --- | --- |
| IDEM-10 | The record is inserted as the **first** write of the transaction, before taking the credit account lock. A concurrent request with the same key blocks on the `UNIQUE` index until the first transaction finishes, then sees the committed record and replays it. Inserting the record at the end would let the second request run the whole operation before failing. |
| IDEM-11 | Deterministic business rejections (e.g. purchase over the available credit, payment over the debt) are stored and replayed like successes. A retry gets the same answer instead of a different one because the balance changed in between. |
| IDEM-12 | Records never expire within the scope of this exercise. |

## 4. Provider webhook

| ID | Rule |
| --- | --- |
| IDEM-13 | The provider's deposit report follows the same rules, with the provider as `principal`. |
| IDEM-14 | The provider is assumed to work correctly: it sends a stable key when it retries the same report. |
| IDEM-15 | The deposit state machine is a second guard: only a `PENDING` deposit can be confirmed or failed (BR-DEP-6), so a report with a new key for an already processed deposit cannot apply its effect again. |
